## 1. 已确认的问题（含代码位置）

### P1 / P3 · 令牌与 PIN 哈希进入备份与同步载荷 🔴

数据流（实测）：

```
useStore.exportData()            useStore.ts:321-334   → 返回 settings: s.settings（整个 Settings）
   ├─ DataPage.handleExport()    DataPage.tsx:67-85    → 下载 xiaojinku-YYYY-MM-DD.json（含 token/pinHash）
   └─ exportSnapshot()           useSyncStore.ts:56-58 → 复用 exportData()
        └─ push(cfg, snapshot)   syncService.ts:79-95  → POST body = { baseVersion, data }
             └─ api.php          api.php:169-176       → $state['data'] = $data 原样落盘
```

涉及字段（`types.ts:68-95`）：
- `settings.sync.token` — 服务器访问令牌（`types.ts:71`）
- `settings.pinHash` — 应用锁 PIN 哈希（`types.ts:78`）

风险：
1. **备份文件泄露 = 令牌泄露**：备份 JSON 存网盘、发给自己、落在电脑回收站，拿到的人可直接读写你服务器上全部账本数据
2. **服务器文件泄露同理**：`xiaojinku.json` 与 `history/snapshot-*.json`（每日一份、保留 30 份）里都躺着明文令牌
3. **PIN 哈希等同明文**：`pin.ts:5-10` 用的是 djb2（32 位、无盐、单轮），4–6 位 PIN 可瞬间离线爆破 → 泄露即等同于 PIN 泄露

### P2 · 导入 / 拉取会覆盖本机锁屏凭据 🟠

```ts
// useStore.ts:336-350  importData
settings: { ...(d.settings ?? 初始), sync: s.settings.sync, lastBackupAt: s.settings.lastBackupAt }
// useStore.ts:388-401  applyRemote
settings: { ...(d.settings ?? s.settings), sync: {...s.settings.sync, version, lastSyncAt}, lastBackupAt: s.settings.lastBackupAt }
```

✅ 已正确保留：`sync`、`lastBackupAt`（符合"导入保护本地同步配置"）
❌ 未保留：`pinHash`、`appLockEnabled`、`theme`

后果：
- 导入他人/他设备的备份 → **本机锁屏 PIN 被替换成对方的**，且 `appLockEnabled` 可能从 `false` 变 `true` → 用户被一个自己不知道的 PIN 锁在门外
- 从服务器拉取数据 → 同样会覆盖本机 PIN 与主题（换设备同步时尤其容易踩到）

### P4 · api.php 读-判-写无锁，并发静默覆盖 🟠

```php
$current = readState();                                    // ① 读
if (!$force && $current['version'] > $baseVersion ...) {}  // ② 判
writeState($next);                                         // ③ 写
```

两个并发请求可能都读到 `version=10`、都通过冲突检查、都基于 10 写入 11 → **先写的被后写的无声覆盖，不返回 409**。
典型触发：手机与电脑同时改、自动同步（2 秒防抖）与手动上传叠加。

附带问题：`$tmp = DATA_FILE . '.tmp'` 是**固定文件名**，并发时两个请求写同一个临时文件，内容可能交错。

### P5 · rename 失败未处理 🟠

```php
$ok = @file_put_contents($tmp, ..., LOCK_EX);
if ($ok === false) return false;      // ✅ 有检查
@rename($tmp, DATA_FILE);             // ❌ 返回值未检查
return true;                          // 无论成败都返回成功
```

rename 失败（磁盘满、权限、跨文件系统）时数据文件仍是旧内容，但接口返回 `200 + 新 version` → **客户端以为同步成功，实际数据没存**。这是最危险的一类：静默丢失，且用户毫无察觉。

（说明：`tmp + rename` 本身保证了写的原子性，所以**读**不会读到半截文件；锁只需解决 read-modify-write 竞态。）

### P6 · 损坏文件被当作空账本 🟠

```php
$j = json_decode($raw, true);
if (!is_array($j)) return ['version' => 0, ...];   // 解析失败 → 当作全新空账本
```

文件损坏/截断/被写坏时，服务器版本号**从 0 重新计数**。其它设备的 `baseVersion` 可能远大于 0 → `max($current, $baseVersion)+1` 虽能兜住，但**冲突检测基准失效**，极端情况下会接受一次本该判为冲突的覆盖。

### P7 · CORS 与令牌传递方式 🟡

- `api.php:32` `Access-Control-Allow-Origin: *`（源码注释已提示应改为自己的域名）
- `api.php:61-63` 支持 `?token=` 查询参数 → **令牌会进入 nginx / Cloudflare 访问日志与浏览器历史**
- 客户端 `syncService.ts:47` 只用 `X-Sync-Token` 头，**从未使用查询参数** → 移除该通道无任何兼容成本

### P8 · DATA_DIR 位置待核实 🟡

`api.php:23` 默认 `__DIR__ . '/data'`（站点内）。按部署记录，实际使用的是站点内 `sync/data`，靠 nginx `location ^~ /sync/data/ { deny all; }` 保护 —— 该规则是否生效需人工 `curl` 验证。

## 2. 目标数据结构：三层分离

| 层 | 内容 | 是否导出 | 是否上服务器 |
|---|---|---|---|
| **① 账本数据 Ledger** | liabilities / categories / transactions / securities / investTxns + 账本级设置 | ✅ | ✅ |
| **② 设备本地配置 Device** | sync（url/token/version/lastSyncAt）、pinHash、appLockEnabled、theme、lastBackupAt、dividendScanAt | ❌ | ❌ |
| **③ 服务器快照** | ① + `{version, updatedAt}` 元数据 | — | — |

### 字段归属表

| Settings 字段 | 归属 | 理由 |
|---|---|---|
| `appLockEnabled` | **设备** | 锁屏是本设备行为；随备份流转会造成"被陌生 PIN 锁住" |
| `pinHash` | **设备** | 凭据，绝不出域 |
| `theme` | **设备** | 外观偏好（当前被导入/同步覆盖属于 bug） |
| `lastBackupAt` | **设备** | 本机备份行为（现状已保留 ✅） |
| `sync`（含 token） | **设备** | 凭据（现状已保留 ✅） |
| `dividendScanAt` | **设备** | 本机扫描节流时间戳，跨设备同步无意义 |
| `defaultCurrency` | 账本 | 数据语义 |
| `fxRate` / `hkdRate` | 账本 | 影响折算结果 |
| `currencySymbolUSD` / `CNY` | 账本 | 展示符号，随账本走 |
| `cashOpening` | 账本 | 参与净资产计算 |
| `costBasis` | 账本 | 持仓成本口径 |
| `dividendIgnored` | 账本 | 用户显式标记"忽略"，跨设备应一致 |
| `isSeed` | 账本 | 数据状态标志（新设备判定依赖它） |

> ⚠️ **待确认**：`dividendScanAt` 与 `dividendIgnored` 的归属。我倾向如上划分（前者设备、后者账本），但 `dividendIgnored` 若你觉得只在本机有效，也可划为设备本地。

### 3.1 新增类型（`src/types.ts`）

```ts
// 可导出 / 可同步的账本级设置
export type LedgerSettings = Omit<Settings,
  'appLockEnabled' | 'pinHash' | 'theme' | 'sync' | 'lastBackupAt' | 'dividendScanAt'>

// 永不出域的设备本地配置

  exported_at: string
  liabilities: Liability[]
  categories: Category[]
  transactions: Transaction[]
  securities: Security[]
  investTxns: InvestTxn[]
```

### 3.2 剥离函数（新增于 `useStore.ts` 或 `src/lib/ledger.ts`）

```ts
// 白名单式剥离：只挑账本字段，任何新增的敏感字段默认不会外流（比黑名单安全）
export function ledgerSettingsOf(s: Settings): LedgerSettings { /* 显式挑字段 */ }

// 兜底断言：上传/导出前校验，含敏感字段直接剔除并告警
export function assertNoSecrets(payload: unknown): void {
  const s = (payload as any)?.settings
  if (s?.sync || 'pinHash' in (s ?? {})) throw new Error('payload contains device secrets')
}
```

### 3.3 `exportData()`（`useStore.ts:321`）

```ts
exportData: () => ({ ..., settings: ledgerSettingsOf(get().settings) })
```

### 3.4 `importData()`（`useStore.ts:336`）

保留现有的"保护本机同步配置"行为，并扩展到 PIN / 锁 / 主题：

```ts
settings: {
  ...(d.settings ?? 初始),                 // 只含账本字段（旧版备份里的 sync/pinHash 会被下一步覆盖）
  appLockEnabled: s.settings.appLockEnabled,   // ← 新增保留
  pinHash: s.settings.pinHash,                 // ← 新增保留
  theme: s.settings.theme,                     // ← 新增保留
  dividendScanAt: s.settings.dividendScanAt,   // ← 新增保留
  sync: s.settings.sync,                       // 现状已保留
  lastBackupAt: s.settings.lastBackupAt,       // 现状已保留
}
```

> 兼容：旧版备份（version 2，settings 含 token/pinHash）导入时，这些字段会被上面的本机值覆盖 → **天然兼容，无需 migrate**。

### 3.5 `applyRemote()`（`useStore.ts:388`）

与上同理，且只更新 `sync.version` / `sync.lastSyncAt`，其余本机配置不动。

### 3.6 `useSyncStore.ts` / `syncService.ts`

- `exportSnapshot()` 保持不变（它复用 `exportData()`，自动受益）
- 在 `push()` 发送前调用 `assertNoSecrets()`（开发期抛错、生产期剔除 + 不上报内容）

### 3.7 关于"新备份被旧版 app 导入"的已知副作用

新版导出不含 `appLockEnabled`（等价 false）→ 旧版 app 导入后**应用锁会被关闭**。
这是安全方向的降级（不会把人锁死），可接受；若需要，可在导出时显式写 `appLockEnabled: false` 让行为更明确。**建议接受并在文档注明**。

## 4. 服务端 api.php 加固方案

### 4.1 加文件锁（解决 P4）

用独立的 `.lock` 文件包裹整个「读 → 判 → 写」临界区：

```php
$lockFile = DATA_DIR . '/.lock';
$lock = @fopen($lockFile, 'c');
if (!$lock) sendJson(['ok'=>false,'error'=>'lock unavailable'], 500);
if (!flock($lock, LOCK_EX)) { fclose($lock); sendJson(..., 500); }
try {
    $current = readState();
    if (!$force && $current['version'] > $baseVersion && $current['data'] !== null) {
        // 409 冲突（在锁内判定，判定与写入之间不再有窗口）
        sendJson([...], 409);
    }
    rotateHistory();
    $next = [...];
    if (!writeState($next)) sendJson(['ok'=>false,'error'=>'write failed'], 500);
    sendJson(['ok'=>true, 'version'=>$next['version'], 'updatedAt'=>$next['updatedAt']]);
} finally {
    flock($lock, LOCK_UN); fclose($lock);
}
```

同时把临时文件名改为唯一：`$tmp = DATA_FILE . '.tmp.' . getmypid() . '.' . bin2hex(random_bytes(4))`，避免并发写同一个 tmp。

### 4.2 rename 结果校验（解决 P5）

```php
if (!@rename($tmp, DATA_FILE)) {
    @unlink($tmp);
    sendJson(['ok' => false, 'error' => 'write failed (rename)'], 500);
}
```

### 4.3 区分"空"与"损坏"（解决 P6）

```php
function readState() {
    if (!is_file(DATA_FILE)) return ['state'=>'empty', 'version'=>0, ...];   // 正常空
    $raw = @file_get_contents(DATA_FILE);
    if ($raw === false)  return ['state'=>'error', ...];                     // 读不了
    $j = json_decode($raw, true);
    if (!is_array($j))   return ['state'=>'corrupt', ...];                   // 损坏
    return ['state'=>'ok', ...];
}
```

- GET 遇到 `corrupt` → 返回 `500 {'error':'data file corrupt'}`，**不得返回 version 0**
- POST 遇到 `corrupt` → 拒绝写入（除非 `force` 且用户明确覆盖），避免把损坏状态版本号化

### 4.4 CORS 与令牌通道（解决 P7）

- 引入 `const ALLOWED_ORIGINS = ['https://xiaojinku.19950920.xyz']`，命中白名单才回显 `Access-Control-Allow-Origin`，否则不返回该头
- **删除 `?token=` 查询参数分支**（客户端从未使用，零兼容成本）
- 预检 `Access-Control-Allow-Headers` 保持 `Content-Type, X-Sync-Token`

### 4.5 纵深防御：服务端也剥离敏感字段

写入前递归剔除 `data.settings.sync`、`data.settings.pinHash`、`data.settings.appLockEnabled`、`data.settings.theme`。
即便有旧客户端上传，服务器也**存不进**这些字段。

> 注意：这**不能**清理已经存在磁盘上的历史数据 → 见第 5 节「存量处置」。

## 5. 迁移、备份与回滚

### 5.1 是否需要数据迁移？**不需要**

关键设计：只改"导出/同步时的剥离"与"导入/拉取时的合并"，**IndexedDB 里的 `settings` 结构保持不变**（仍是完整 `Settings`，persist version 保持 6，`migrate` 不动）。

→ 用户数据零迁移风险，改完打开 app 立刻可用，不存在"升级后账本打不开"的场景。

### 5.2 改动前的备份步骤

```bash
# 1) 应用内：设置 → 数据备份与导入 → 导出 JSON（保存到电脑）
#    注意：这是改进前的产物，含明文令牌，请按敏感文件保管，改进后建议重新导出一份替换

# 2) 服务器（SSH）
cd /www/wwwroot/xiaojinku.19950920.xyz/sync/data
cp xiaojinku.json ~/xiaojinku.bak.$(date +%F).json
cp -r history ~/xiaojinku-history.bak.$(date +%F)

# 3) 代码：当前 main 干净（4ffe058），改动前可打 tag
git tag pre-security-2026-10-28
```

### 5.3 回滚方案

| 层 | 回滚方式 |
|---|---|
| 前端 | `git revert` 或 `git checkout 4ffe058 -- app/src`，重新 `npm run build` 并覆盖站点 |
| 服务端 api.php | 用改动前备份的 `api.php` 覆盖（或 `git checkout 4ffe058 -- app/deploy/api.php`） |
| 服务器数据 | 用 5.2 的 `xiaojinku.bak.*.json` 覆盖 `xiaojinku.json` |
| 浏览器端 | 无需回滚（数据结构未变）；极端情况用「设置 → 导入 JSON」导回备份 |

### 5.4 存量令牌处置（重要，需你决定）

改完代码后，**服务器上已有的明文令牌仍然躺在 `xiaojinku.json` 和 30 份历史快照里**。建议：

1. 生成新令牌：`openssl rand -hex 24`
2. 写入 `token.txt`（新旧令牌可短暂并存？不建议——api.php 当前只支持单令牌）
3. 各设备「设置 → 云同步」填入新令牌
4. 删除 `history/` 下含旧令牌的快照，或等其自然滚动（30 天）

⚠️ 这一步会**短暂中断同步**（填新令牌前），需你选择执行时机。也可以先只改代码、不轮换（接受历史文件里仍有旧明文令牌）。

## 6. 回归测试计划

现有基建：`app/verify_*.mjs`（puppeteer-core + 本地 http 服务），其中 `verify_sync.mjs` 用 Node 起的**模拟 api.php**（契约一致，含 409），`verify_export.mjs` 验证导出。

### 新增 `verify_sync_secrets.mjs`（5 项，对应你的要求）

| # | 用例 | 断言 | 能否本地执行 |
|---|---|---|---|
| T1 | 备份文件不含同步令牌 | 导出 JSON 文本中**不含** token 字符串、不含 pinHash | ✅ 可（puppeteer） |
| T2 | 同步请求载荷不含令牌 | `page.on('request')` 抓取 POST body，断言不含 token/pinHash | ✅ 可 |
| T3 | 导入不改变本机同步凭证 | 预置 sync(url/token)+pinHash → 导入伪造 JSON（含不同 token/pinHash）→ 断言本机值不变 | ✅ 可 |
| T4 | 并发冲突不静默覆盖 | 同 baseVersion 并发两个 POST → 断言 200 / 409 各一，而非两个 200 | ⚠️ **见下** |
| T5 | 损坏数据文件不被当空账本 | 服务端放非法 JSON → GET 返回 500（非 version 0），客户端不覆盖本地 | ✅ 可（模拟服务端） |

**T4 的说明（不谎报）**：
- 沙箱**无 PHP**（已确认 `which php` 无输出），无法在本地跑真实 `api.php`
- 因此 T4 分两段：
  - **T4a（本地可执行）**：用 Node 模拟"加锁后的服务端契约"，验证**客户端**在收到 409 时不静默覆盖、会弹冲突框
  - **T4b（需人工在服务器执行）**：真实 PHP 环境下的并发验证，脚本会附在交付物里（一个 `curl` 并发脚本或 PHP 自测脚本），由你在服务器跑 → **我不会声称它已通过**
